# v14 批量处理调查与修复

目标版本：0.3.3-preview2 / versionCode 14。保留v13测光、相纸与印放功能；以独立公开测试标签发布，历史v12保留。

## 复现证据

2026-11-16，在Redmi K80 Pro（24122RKC7C / Android API 36）上，用用户已授权的6张4096×3072 HEIF和原有编辑，测试原尺寸导出。照片、URI、文件名、编辑记录及私人截图不进入仓库。

测试基线是安装了未修复批量逻辑的v13 Debug；不是宣称对压缩v12 Release执行了引用Kotlin类的JUnit。首次6张JPEG导出全部失败：第一张报`Vulkan compute dispatch failed (VkResult -4)`，后面五张报`Vulkan upload failed (VkResult -4)`。这是GPU设备失效后继续使用失效引擎的证据，不能单凭此认定内存不足。

同一未修复版本再次运行6张，全部成功（约45.5秒）。单张原尺寸分别保留全部设置、关闭颗粒、关闭测光、同时关闭，四组也都成功。因此首次GPU中断的触发条件尚未查明；没有把颗粒、测光或IIR模糊推测当作已证实原因，也没有为了测试通过而关闭这些功能。

基线100张隔离导入探针的元数据读取约113毫秒，分窗读取全部缩略图总计约2.43秒，主线程16毫秒心跳最大间隔23毫秒。这个探针不包含Compose界面绘制，不能据此宣称实际列表完全不卡顿。系统`loadThumbnail`与现有240长边解码差距较小，没有据此替换解码器或添加依赖。

## 改动

- 捕获`VK_ERROR_DEVICE_LOST` / `VkResult -4`后，销毁失效引擎，重建并按同一输入、尺寸和参数重试一次。连续两次失效也会清除坏引擎，避免带给下一张。其他错误不盲目重试。
- 批量仍逐张处理，不同时渲染多张原尺寸图片；保留原图、颗粒、测光、曝光、相纸和用户选定的输出格式。
- 完成或停止后保留成功数、失败数、逐张原因；仅重试失败条目，不重复保存成功项。失败诊断可从“关于”复制。
- 导入先去重，按8张一组在IO线程读取信息，显示进度，防止重复启动导入；列表仍按需读取240长边缩略图，不在导入阶段跑全部胶片渲染。
- JNI错误日志保留引擎进度，便于后续定位首次设备失效；没有修改材料数据、核心着色器或色彩计算。

本轮测试后核对原照片库和配方JSON，与测试前相同。最后的公开示例UI检查可新增内置示例，不修改这6张私人照片的编辑。自动测试只清理自身创建的文件或新导出，不删除历史输出、原片或私人编辑。

100张导入测试使用本地FileProvider文件，覆盖应用内读取与列表，不测云相册下载或系统选择器返回前的耗时。主线程心跳不是完整帧率统计，92毫秒仍可能产生短暂掉帧，不能称为全程零卡顿。首次设备失效条件仍未完全定位；新增的恢复与诊断不等于驱动问题已被彻底消除。

安装包约12.17 MiB，versionCode 14，签名与本地v12相同，可覆盖安装。核心预构建库SHA256与v12相同；JNI增加生命周期恢复和错误进度记录。主机diff检查和单独代码审查未发现确定的严重或重要缺陷。已移除开发测试工具，手机保留最终Release应用。

限制：这不是所有安卓设备的兼容性保证；50MP、HDR、其他厂商驱动与编码器仍需单独测试。进程被系统终止后不自动续传批量任务。
