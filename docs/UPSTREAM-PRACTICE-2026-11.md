# 上游同输入实测与吸收

这次实际执行了上游代码，不以项目介绍或材料名称代替结果。实验固定 SpektraLab `0b5acfc4e45b7a946ed33a3c4b4e60429d208b66`、spektrafilm `3bb2c2d2801ff68b92019cf1dbcbb133d60832bc`，并从片屿仓库当前 `engine/` 重新编译 Windows Vulkan DLL。

## 如何比较

同一组输入：海湾、玫瑰、小教堂、人像、雨夜五张已披露的AI输入，以及两张署名许可的真实小米手机JPEG。统一解码为 encoded sRGB、长边640、相同像素数组；显式打开输入传递函数解码、使用sRGB输出、关闭自动曝光/颗粒/光晕/眩光/场景纬度。扫描器锐化保留两侧相同默认值。模型比较不混原图，不加片屿预设。

五组共有材料：Portra 400 + Portra Endura、Vision3 250D + 2383、Provia 100F、Velvia 100、Kodachrome 64；后三者直接扫描正片，跳过相纸。七图×五组×三个实现，共105个基线输出，保存完整参数、输入输出哈希和原始浮点/16位结果。

另外完成 SpektraLab 前曝光±0.7EV共70个输出、片屿当前模型+0.7EV共35个输出、Python参考+0.7EV共15个输出，合计225个基础受控输出。再按Android JNI实际使用的256行条带执行方式重跑两套原生引擎的35个+0.7EV组合，追加70个输出，总计295个。没有把重复渲染次数当成不同照片数量。

联系表逐张查看了海湾、花丛、街景及其他题材：在这个统一配置下，三个实现没有可见的整体色彩差异。Portra/2383纸基色彩倾向、正片的响应都被保留。当前材料核心没有证据支持为“升级颜色”而重写；最新HDR与minilab控制修复也没有改变此次SDR、默认印片设置的输出。

这是Windows同算法实验，不能冒称最新Mac应用的完整界面、RAW解码或Android逐像素验证。Android的图像解码、8位回读、片屿强度混合/额外调色属于另一个边界。800T衍生模型和Acros II扩展未纳入五款共同材料的Python一致性结论。此前真机样片仍独立保存。

## 学到了什么，改了什么

上游在进入胶片响应前调整 `exposure_compensation_ev`，片屿旧曝光是在成片sRGB上乘增益。两者不仅数值意义不同，响应形状也不同；负片还会受默认印片曝光补偿影响。

实验同时检查了相同EV和匹配全图RGB均值的结果，避免用亮度差冒充层次改善。匹配均值后，玫瑰的花瓣/叶片关系、人像的肤色、Provia天空与山体、Kodachrome白墙与绿色仍不能由单一后期增益等价重现。前曝光不是“任何照片都更好看”，而是用户选择胶片工作位置的创作能力。

片屿0.3.2 versionCode8新增 **胶片曝光**（±2EV）：直接调用已有上游引擎参数，不改profile，不用后期HSL伪造。原 **曝光** 保留成片提亮功能，旧配方默认 `filmExposure=0`，不会改变旧效果。新值进入预览缓存、照片库缩略图、撤销/重做、配方持久化和单张/批量导出；CPU完成层不重复应用。两种曝光在界面分别说明。

想看完整材料模型，可关闭片屿预设并把风格强度设为100，再用胶片曝光做少量调整。片屿额外预设仍是公开的审美配方，不能与材料测量混为一谈。

JPG/HEIF可进入同一个胶片模型，但反传递函数不能撤销手机的局部HDR、降噪与锐化，更不能恢复已剪掉的高光。无需RAW才能创作胶片风格，不等于JPG有RAW的全部余量。

## 复现与验证边界

实验脚本、每张参数/哈希、联系表与数值摘要随测试资料归档；资料包还包含7张原始输入及对应的640长边解码PNG，手机JPEG保留作者、来源和CC BY-SA 4.0许可记录。完整浮点结果留本地研究目录。Windows构建仅用外部CMake包装解决MSVC导入库同名、缺少`<algorithm>`包含问题，没有改上游渲染算法。运行环境使用Python3.13，依赖版本单独记录。

versionCode8的编译/lint及真机验收状态以交付目录的最终验证记录为准；不能用versionCode7已通过的26项真机测试替代新控制验证。历史扫描参考的异场景色彩仍有差距，本次模型一致性不能证明历史照片已经被准确复刻。
